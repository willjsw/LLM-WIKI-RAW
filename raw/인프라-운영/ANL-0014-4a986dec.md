# 콜 처리 서버에 AOP 구조화 로그를 도입할 때의 설계 논점

## Analysis

코드리뷰 메모에서 나온 논점을 정리했다. 일부는 결론이 아니라 논의 중 의견이다.

**적용 범위 제외.** gRPC 구독처럼 지속적으로 들어오는 스트림 요청에 공통 AOP 로깅을 걸면 로그가 폭증한다. 제외용 어노테이션을 만들어 AOP 적용 범위와 구조화 로그에서 빼고 콘솔 로그에만 남겼다. 이벤트성 값(예: DTMF 입력)은 최종값을 한 번만 찍는다.

**출력 방식.** 비동기 로그 출력을 JSON 동기 출력으로 바꿨다. 로거 이름이 애스펙트 클래스로 찍히는 문제, 스트림 구독에서 난 에러를 어디로 모을지도 함께 정해야 한다.

**AspectJ 와 스프링 Bean.** AspectJ 로 위빙한 애스펙트는 스프링이 만든 객체가 아니므로, Configuration 에서 애스펙트 인스턴스를 가져와 Bean 으로 등록해야 스프링 의존성을 쓸 수 있다.

**메시지 직렬화.** 외부 인터페이스는 Protobuf, 내부 로그·이벤트는 JSON 으로 표현하자는 의견이 나왔다. gRPC 메시지는 protobuf 의 JSON 변환 유틸로 바꾼다. Proto 메시지를 JSON 으로 통째로 넣으면 필드가 추가·변경될 때 문서화와 최신 유지 비용이 생기므로 Mapper 로 필요한 필드만 옮기는 방식도 검토 대상이다.

**세션 상관 ID 설계.** 통화 단위 상관 ID 를 SIP Call-ID 로 삼지 않은 이유는 아웃바운드 통화에서는 처리 시작 시점에 그 값이 없기 때문이다. 대신 세션 시작 순간 반드시 존재하는 내부 대화 ID 를 기준으로 하고, prefix ID 는 한 번만 생성해 규칙대로 붙인다(유틸 호출마다 값이 바뀌지 않게). 세션이 맺어지기 전의 미디어 로그는 나중에 매핑 테이블에서 조회해 찍어야 한다.

**운영 인터페이스.** 함께 제안된 것: 런타임 로그 레벨 변경, 모니터링(실행 중 세션·미디어 자원 수와 사용량, 특정 세션 추적, 시간별 누적), 헬스 체크(Actuator 사용 가능). 서버 간 연결 체크 같은 공통 이벤트는 각 서버 코드에 넣기보다 중간 이벤트 브로커(예: Redis Stream)를 거치게 하자는 의견이 있었다.
