# 결재로만 실행되는 운영 DB 에 스키마 변경을 반영하는 절차

## Purpose

운영(고객사) DB 에 도구가 직접 붙을 수 없고 DBA 가 결재된 SQL 만 실행하며 결과는 화면 캡처로만 받을 수 있을 때, Git 정본 형상으로 DB 를 맞추고 그 결과를 검증한다.

## Steps

1. 기준 커밋(마지막 반영 시점)과 최신 커밋의 정본을 로컬 DB 두 개(PRE, POST)에 설치해 기대값 추출용으로 쓴다. 설치가 실패하면 '정본만으로 재현 불가'로 보고 멈춘다.
2. 테스트 DB 와 PRE 를 비교해 이탈분을 찾고, 각 이탈분의 출처 커밋을 `git log -S` 등으로 찾는다. 못 찾으면 Git 을 거치지 않은 직접 반영이므로 멈추고 사람에게 보고한다.
3. 테스트 DB 와 POST 의 차이로 증분 쿼리를 DDL / DML(시드) 로 나눠 작성한다. 항목마다 근거 커밋을 붙이고, 데이터가 지워지는 변경은 행 수를 제시해 확인을 받는다.
4. 적용 전(pre_commit)·적용 후(post_commit) 검증 쿼리 두 벌을 같은 구성으로 만든다. 기대값만 다르다.
5. 테스트 DB 에서 한 트랜잭션으로 증분 → post_commit → ROLLBACK 하는 Dry-Run 을 정순·역순 두 번 돌려 PASS 가 될 때까지 증분을 고친다.
6. 증분 적용 전 테스트 DB 에 pre_commit 을 조회로 실행해 전부 PASS 인지 본다(검증 쿼리 자체의 신뢰성 확인).
7. 현장 실행자용 README(순서, 파일별 데이터 영향·재실행 가능 여부·잠금 대상, 촬영 안내)를 쓴다.
8. 사람이 테스트 DB 에 실제 적용(COMMIT)하고 post_commit 으로 확인한다.
9. 현장: pre_commit 실행·요약 사진 → 전부 PASS 가 아니면 멈춘다 → DBA 권한 파일 → DDL → DML → post_commit 실행·사진.
10. 사진을 표로 옮겨 요약 행 건수와 상세 행 수를 대조하고, 불일치는 원인(미적용·부분 적용 / 증분 오류 / 현장 고유 차이 / 검증 쿼리 오류)으로 분류해 다음 번호의 보정 파일을 만든다.

AI 에이전트에 맡길 때는 비교·작성·롤백 Dry-Run·조회까지만 허용하고, 실제 반영·Git 커밋·데이터 삭제 판단은 사람이 한다.
