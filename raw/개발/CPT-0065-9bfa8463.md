# JVM OutOfMemoryError 유형별 원인과 대응

## Definition

JVM의 OOM은 Heap Space, Method Area(Metaspace), Native Area 중 어느 영역에서 났는지에 따라 원인과 조치가 전혀 다르므로, 메시지로 영역을 판별하는 것이 트러블슈팅의 첫 단계다.

## Evidence

| 메시지 | 원인 | 대응 |
|---|---|---|
| Java heap space | 트래픽 증가, 회수되지 않게 참조를 붙든 코드(누수) | 최대 Heap 조정 + 누수 수정 |
| GC overhead limit exceeded | 98% 이상 시간을 GC에 쓰고 2% 미만만 회수하는 상태가 연속 | 덤프 확보 후 누수 분석 |
| Permgen space / Metaspace | 로드된 클래스·static 증가, 동적 클래스 생성 | 동적 클래스 생성 로직 점검, Metaspace 상한 설정 |
| unable to create new native thread | 스레드는 네이티브 메모리에 생성, ulimit 제약, 스레드 누수 | ulimit 확인, Heap 축소, 스레드 누수 수정 |
| Requested array size exceeds VM limit | Heap보다 큰 배열 요청 | 코드 수정 |
| Kill process or sacrifice child | OS의 OOM Killer(JVM이 아님) | 메모리 증설, 프로세스 분리 |

- ulimit: root가 일반 계정에 Hard limit을 주고 일반 계정은 그 안에서 Soft limit을 정한다. nofile 초과 시 Too many open files가 난다
- Heap OOM 중에는 CPU가 GC에 집중되어 서비스가 극도로 느려진다
- 전역(application scope) 컬렉션에 요청마다 객체를 쌓는 코드는 GC Root에서 항상 도달 가능해 전형적 누수가 된다
