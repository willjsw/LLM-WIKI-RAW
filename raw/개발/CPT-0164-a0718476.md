# SIP ACK, BYE, CANCEL 의 구분과 경쟁 조건

## Definition

통화를 끊는 요청은 상태에 따라 다르다. 최종 응답(200 OK) 전, 즉 벨이 울리는 중에는 CANCEL, 통화가 성립한 confirmed dialog 에서는 BYE 를 쓴다. ACK 는 INVITE 의 최종 응답을 받았다는 확인이며 응답이 없다.

## Evidence

- 2xx 에 대한 ACK 는 end-to-end 다. UA 가 직접 만들어 200 OK 의 Contact 로 보내고 branch 는 새 값이며 SDP 를 실을 수 있다(late offer 의 Answer). 3xx~6xx 에 대한 ACK 는 hop-by-hop 이다. 트랜잭션 계층이 자동 생성하고 원 INVITE 와 같은 목적지·branch 이며 바디가 없다.
- ACK 에는 응답이 없어 유실돼도 보낸 쪽은 모른다. 상대가 200 OK 를 계속 재전송하는 것이 유일한 신호다.
- early dialog(180 Ringing 중)에 BYE 를 보내면 `481 Call/Transaction Does Not Exist` 가 돌아온다.
- CANCEL 은 최종 응답이 오지 않은 INVITE 만 대상이며 CSeq 번호와 branch 를 대상 INVITE 와 같게 한다. 응답은 두 개다(CANCEL 의 200 OK + 원 INVITE 의 `487 Request Terminated`). 487 에도 ACK 를 보낸다. hop-by-hop 이라 프록시가 분기별로 다시 만든다.
- 경쟁 조건: CANCEL 을 보내는 순간 상대가 이미 200 OK 를 보냈다면 CANCEL 은 무시된다. 이때는 200 OK → ACK → BYE 순으로 정리해야 하며, "끊었는데 통화가 연결된" 증상의 원인이다.
- 같은 맥락의 충돌: 양쪽이 동시에 re-INVITE 를 보내면 `491 Request Pending` 이며 랜덤 시간(UAC 쪽 2.1~4초) 대기 후 재시도한다.
