# Redis Stream 키 네이밍 경계 도메인 이벤트 구조

## Definition

스트림 키를 `<env>:<channel>:<boundary>:<domain>:<event>:{<partition>}` 로 구성하면 키에 수신자를 넣지 않아 구독 모듈이 늘어도 키 의미가 유지된다. boundary 는 in(외부→내부)·out(내부→외부)·core(내부 간) 셋으로 나눈다.

## Evidence

- `<발행 모듈>:<수신 모듈>` 형태는 구독자가 추가되면 이름과 실제 사용이 어긋난다.
- in/out 만 두면 내부 이벤트가 in 에 섞인다. core 를 두면 경계를 넘는 트래픽만 in/out 에 남는다.
- 예: `PROD:CHAT:in:gateway:msg-received:{room-1024}`, `PROD:CHAT:core:chat:msg-persisted:{room-1024}`, `PROD:CHAT:out:push:notify-requested:{room-1024}`.
- 이벤트 이름 규칙: 과거형(`msg-persisted`)은 사실 통지로 여러 그룹이 각자 구독(fan-out)하고, `-requested` 접미사는 작업 지시로 단일 그룹이 소비(work queue)한다.
- Consumer Group 이름은 `<모듈>[-<용도>]`.
- 트레이드오프: 키만 보고 구독자를 알 수 없으므로 구독 관계를 코드 상수나 레지스트리에 모으고 운영 중에는 `XINFO GROUPS` 로 확인한다.
- 무중단 키 이전 순서: 발행 측 신규 키 동시 발행 → 수신 측 그룹 전환 → 구 키 드레인.
- 확정 전 제안안이다.
