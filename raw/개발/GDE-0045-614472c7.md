# SIP 통화 장애 패킷 진단 순서

## Purpose

등록 실패, 착신 불가, 통화 끊김, 단방향 음성 같은 SIP 장애를 패킷으로 원인 구간을 좁혀 찾는다.

## Steps

1. 캡처부터 한다. `tcpdump -i any -s0 -w /tmp/sip.pcap 'port 5060 or portrange <RTP 대역>'` 처럼 `-s0` 으로 잘리지 않게, RTP 포트 대역까지 포함해 뜬다. 가능하면 양쪽에서 동시에 캡처하고 시각을 NTP 로 맞춘다.
2. 흐름은 `sngrep` 이나 Wireshark 로 시퀀스 다이어그램으로 보고, 필요한 필드는 tshark 로 뽑는다(예: REGISTER 의 CSeq, Call-ID 별 흐름).
3. 패킷이 도달하는지 본다. 안 오면 방화벽·라우팅·서버 주소, 포트 개방(`ss -lunp | grep 5060`)을 확인한다.
4. 응답이 오는지 본다. 재전송만 반복되다 32초에 끝나면 Timer B/F 타임아웃이므로 경로와 상대 서버 로그를 본다.
5. 응답 코드를 해석한다. 401 무한 반복은 CSeq 미증가·nonce 재사용, 403 은 계정·realm 불일치(재시도 금지), 423 은 Min-Expires, 480 은 상대 미등록, 481 은 다이얼로그 불일치(로컬 세션 정리), 488 은 SDP 공통 코덱 없음, 491 은 동시 re-INVITE, 503 은 Retry-After 대기.
6. 2xx 뒤 ACK 가 오가는지 본다. 200 OK 가 반복 재전송되다 약 32초 뒤 BYE 가 나가면 ACK 유실이며 Contact 주소 도달성, NAT, Record-Route 를 점검한다.
7. RTP 가 양방향인지 본다. 한쪽만이면 SDP `c=` 라인 IP(사설 IP 여부)와 RTP 포트 방화벽을 확인한다.
8. 간헐 실패면 메시지 크기를 본다. 1300바이트를 넘으면 UDP 단편화가 의심되므로(`tshark -Y 'ip.flags.mf == 1 || ip.frag_offset > 0'`) TCP 전환이나 긴 헤더 목록 축소를 시험한다.
9. 등록 직후 끊기면 200 OK 의 expires 와 실제 재등록 간격을 비교한다.
10. 캡처를 공유하기 전에 계정명·전화번호·nonce·response 해시를 마스킹한다(예: sed 로 `response="..."`, `nonce="..."` 값과 긴 번호를 치환).
