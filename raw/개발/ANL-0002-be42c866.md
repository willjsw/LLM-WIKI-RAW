# 상태 행 즉시 갱신형과 raw 보존 이벤트 소싱형 통계 수집 비교

## Analysis

콜 이벤트 통계 수집기를 두 방식으로 비교한다.

| 축 | 상태 행 즉시 갱신형 | raw 보존 이벤트 소싱형 |
|---|---|---|
| 이벤트 의미 | 이벤트 = 쓰기 명령. 오는 즉시 상태 행을 INSERT/UPDATE | 이벤트 = 사실 축적. 판정은 정책 테이블로 분리 |
| 원본 | 보존하지 않음 | raw를 불변으로 저장, leg/session 스냅샷 별도 |
| 집계 시작 | DB 프로시저가 주기적으로 종료 행을 긁어 감 | 세션이 확정되면 그 시점에 집계 대상으로 핸드오프 |
| 늦은 이벤트 | 이미 쓴 행을 고칠 수 없음 | late 표시와 재확인으로 흡수 |
| 규칙 변경 | 잘못 기록된 상태를 되돌릴 원본이 없음 | raw로 재계산할 여지가 있음 |

- 즉시 갱신형은 구조가 단순하지만, 판정 규칙이 쓰기 로직에 박혀 있어 규칙 하나가 틀리면(예: 보류 이벤트를 통화 중으로 기록) 데이터가 영구히 오염된다.
- 이벤트 소싱형은 수집과 판정, 확정과 집계를 분리해 재계산 가능성과 늦은 이벤트 흡수 능력이 좋아진다. 대가로 세션 그래프, 확정 조건, 핸드오프 테이블 같은 구성 요소가 늘어난다.
- 두 방식 모두 전달 보장 수준(at-most-once)과 단일 JVM 전제가 같을 수 있다. 구조를 바꾼다고 전달 보장이 자동으로 올라가지는 않으므로 ACK 시점과 dedup은 따로 설계해야 한다.
- 레거시에서 가져갈 만한 아이디어: 고정 consumer group으로 재기동 후 이어 읽기, 기동 시 활성 콜을 DB에서 복원, 스케줄러 클러스터링으로 중복 실행 방지, 같은 배치 안 동시각 이벤트를 메시지 유형 우선순위로 정렬.

근거는 정적 코드 분석이며 실행으로 검증하지 않았다.
