# NAT 환경에서 SIP 가 깨지는 원리와 해결책

## Definition

NAT 는 패킷의 IP 헤더만 바꾸고 SIP 메시지 본문(Via, Contact, SDP `c=`) 안의 IP 는 바꾸지 않으므로, NAT 뒤 단말이 적어 보낸 사설 주소로는 서버나 상대가 되돌려 보낼 수 없다. 실무에서 등록·착신·단방향 음성 문제의 상당수가 여기서 나온다.

## Evidence

- 증상: 등록은 됐는데 전화가 안 온다(Contact 에 사설 IP), 한쪽 소리만 안 들린다(SDP `c=` 가 사설 IP), 일정 시간 뒤 착신이 끊긴다(NAT 매핑 만료).
- rport/received(RFC 3581): 단말이 Via 에 값 없는 `rport` 를 붙이면 서버가 실제 출발지 IP·포트를 `received`/`rport` 로 채워 응답하고, 이후 그 주소로 요청을 보낸다. NAT 매핑이 살아 있는 동안 안쪽까지 도달한다.
- keep-alive: NAT 매핑은 무응답이 이어지면 사라진다(UDP 는 장비마다 다르나 보통 30~180초, 실제 값은 장비 설정을 확인해야 함). CRLF 핑(RFC 5626, 가장 가벼움), OPTIONS 핑(생존 확인 겸), 짧은 expires(트래픽 최대) 중 하나로 매핑 타임아웃보다 짧은 주기(UDP 는 30초 내외)로 보낸다.
- Path 헤더(RFC 3327): 경계의 엣지 프록시(SBC)가 REGISTER 에 Path 를 추가해 "이 단말로 가는 요청은 나를 거쳐라"를 바인딩과 함께 저장시킨다. REGISTER 에 `Supported: path` 가 필요하다.
- Outbound(RFC 5626): `reg-id` + `instance-id` 로 단말별 연결(flow)을 식별해 다중 엣지 등록과 장애 시 재연결을 체계화한다.
- 진단: 캡처에서 IP 헤더의 출발지와 Contact·Via·`c=` 의 IP 가 다른지 비교한다(예: `tshark -r x.pcap -Y sip -T fields -e ip.src -e sip.Contact`).
