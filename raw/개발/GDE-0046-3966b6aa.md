# C 장기 실행 프로세스의 메모리 누수 검증 절차

## Purpose

데몬처럼 오래 도는 C 프로세스에서 정적 분석으로 찾은 누수·오버플로 후보를 확인하고, 수정 뒤 회귀가 없는지 검증한다.

## Steps

1. 판정의 전제(라이브러리 함수별 반환값 소유권)를 먼저 표로 확정하고, 후보마다 근거 코드와 신뢰도(확정/의심)를 적는다. 오탐 배제 근거도 따로 남긴다.
2. 빌드 경고를 최대화한다(`-Wall -Wextra -Waddress -Wformat=2 -Wstringop-overflow=4`).
3. 정적 분석기를 돌린다(`cppcheck --enable=all --inconclusive -I <헤더 경로> <소스 경로>`).
4. 힙 누수는 Valgrind 로 대상 프로세스만 감싸 기동한다(`valgrind --leak-check=full --show-leak-kinds=all --track-origins=yes --log-file=<경로> ./<프로세스>`).
5. 오버플로·경계 문제는 AddressSanitizer 빌드로 확인한다(`CFLAGS += -fsanitize=address -fno-omit-frame-pointer`, `LDFLAGS += -fsanitize=address`).
6. 공유메모리·자체 풀에 있는 자원은 Valgrind 가 누수로 잡지 않는다. 풀 사용 슬롯 수와 관련 카운터(등록 수 등)를 주기적으로 로그로 남겨 확인한다.
7. 경로별 부하 시나리오를 수천 회 반복한다: 정상 경로(등록 → 해제 → 재등록), 인증 실패 경로, 응답 없이 방치하는 타임아웃 경로, 처리 중 하위 프로세스 강제 종료, 비정상적으로 긴 입력.
8. 각 시나리오 전후로 RSS(`/proc/<pid>/status` 의 VmRSS), 풀 사용 슬롯 수, 업무 카운터 세 값을 비교한다. 정상이라면 모두 시나리오 전 수준으로 돌아와야 한다.
9. 수정은 심각도×수정 난이도로 나눠 국소 수정(한두 곳, 효과 큼)부터 하고, 해제 코드 복원처럼 동작이 바뀌는 수정은 영향 경로 전체 회귀 테스트와 함께 한다.
