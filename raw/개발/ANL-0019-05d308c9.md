# REST 기반 채팅 메시지 순서 보장 방안

## Analysis

웹소켓은 한 연결 안에서 메시지가 순서대로 오므로 연결 단위로 순서를 보장하기 쉽다. 반면 고객 시스템과 REST로 연동하면 요청마다 stateless하게 여러 게이트웨이 인스턴스로 흩어져 들어오므로 순서가 깨질 수 있고, 상담사 발신 방향도 같은 문제가 있다.

검토한 방안:
- 대화 ID(conversationId)를 해시해 Redis Stream 파티션을 고르고, 한 파티션은 한 소비자만 읽게 한다(카프카 파티션과 같은 원리). 같은 대화의 메시지는 항상 같은 순서 경로를 탄다.
- 게이트웨이는 stateless로 두고 수평 확장하며, 순서 보장 책임은 파티션 배정에 둔다.
- 소비 노드가 죽으면 다른 노드가 그 파티션을 이어받아야 하고, ACK 타임아웃이 지난 미처리 메시지는 재처리·복원한다.
- 이 구조가 없으면 대화 단위 Lock으로 직렬화해야 하므로 처리량이 떨어진다(목표 최소 100 TPS).
- 대안으로 sticky session도 있지만 노드 장애 시 재배치 문제는 그대로 남는다.
