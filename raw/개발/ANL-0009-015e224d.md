# 검증을 위험이 생기는 시점에 맞춰 배치하기

## Analysis

**가설.** 커밋마다 전체 검증을 두 번(커밋 전 + post-commit) 돌리는 구조에서는 에이전트가 생각하는 시간보다 검증을 기다리는 시간이 더 크다.

**측정.** 로컬 실행 지표로 보면 전체 검증 337회 중앙값 241초, 그중 87%가 회귀 테스트 파일 하나였다. 실패는 9건뿐이라 나머지는 통과 확인에 4분씩 썼다. 구현자 시간의 약 41%가 검증 대기였고, 120건은 직전 실행 종료 60초 안에 같은 트리를 다시 검증한 것(post-commit)이었다. 비싼 검증은 10종 중 둘뿐이고 나머지 8종은 합쳐 1초 미만이었다. 최근 커밋의 23%는 문서만, 3%는 UI 만 바꿔 비싼 테스트가 막을 위험이 없었다.

**판단 기준.** 같은 위험을 막는 검증은 그 위험이 생기는 시점에 한 번이면 충분하다. 시점은 셋이다.
1. 변경이 생길 때(커밋): 되돌리기 어려운 것(시크릿, 형식, 생성물 불일치)은 저렴하므로 여기서 매번 막는다.
2. 사람이나 리뷰어에게 넘길 때(push·MR·재시도 회차 끝): 깨진 코드로 리뷰 회차를 쓰지 않도록 여기서 녹색이어야 한다.
3. 통합 브랜치에 들어갈 때(머지): 서버 측에서 강제할 수 있는 유일한 지점이며 CI 가 맡는다.

**재배치안(4층).** L0 즉시(명령·커밋마다 1초 미만 검사) / L1 변경 영역(task 커밋 전, 바뀐 경로에 걸린 검증만, 분류 안 되는 경로가 하나라도 있으면 전체 — 미탐보다 과탐) / L2 전체(push 직전 1번) / L3 CI 머지 게이트. 경로와 검증의 대응은 리포마다 다르므로 설정에 둔다. post-commit 재검증은 끄거나 캐시로 즉시 끝나게 한다.

**잃는 것.** 중간 커밋 하나하나가 녹색이라는 보장이다. merge commit 으로 머지하는 리포는 중간 커밋이 이력에 남아 `git bisect` 에서 이 보장이 쓰인다. 그래서 규칙 변경은 ADR 로 결정하고, 대안으로 squash 머지나 `git bisect --first-parent` 를 검토한다. 규칙을 바꾸지 않는 개선(캐시, 중복 실행 제거)을 먼저 적용해 얻은 몫을 본 뒤 규칙 변경이 더 얻는 몫과 비용을 사람이 비교한다.

**결과.** 경로 조건·통과 기록·병렬화를 적용해 같은 작업 형태(커밋 11개, push 3번)를 재현하니 검증 대기가 166.9분에서 3.2분, 이슈 전체가 213.6분에서 약 49.9분이 됐다.

**하지 않는 것.** 리뷰 회차 상한·반복 정지 완화(루프 종료를 보장하는 안전망), 사람 게이트 제거(게이트를 거치는 이슈 수를 줄이는 쪽으로), 이미 짧은 단계(리뷰어 약 2분)의 경량화.
