# PEL과 목적지별 전달 큐의 ACK 경계 분리

## Definition

Redis Stream 의 PEL 은 컨슈머가 읽고 아직 `XACK` 하지 않은 항목만 추적하고, 목적지별(브라우저 탭별 표시, 외부 시스템 처리) 완료는 기록하지 못한다. 목적지가 여럿이거나 완료 확인이 늦는 경우 Stream 이벤트를 목적지별 공유 큐로 옮긴 뒤 XACK 하고, 전달 완료는 큐에서 따로 관리한다.

## Evidence

- 다중 탭: 대화별 LIST 큐에 순서대로 적재하고 소켓마다 ACK 커서를 둔다. 살아 있는 소켓들의 최소 ACK 위치까지만 큐 앞을 정리해 한 탭의 ACK 가 다른 탭의 미전달 이벤트를 지우지 않게 한다.
- 외부 HTTP 목적지: 대화별 큐와 송신 락을 두고 맨 앞 한 건만 보낸다. 결과가 확정되기 전에는 뒤 이벤트를 보내지 않으며, 실패나 타임아웃이면 항목을 남겨 같은 `eventId` 로 재시도한다.
- 큐 확인 알림은 Pub/Sub 으로 보내되, 알림 유실에 대비해 소켓 보유 인스턴스가 자기 활성 대화의 큐를 주기적으로 확인한다.
- Sentinel 장애 조치 때 비동기 복제로 Redis 상태가 되돌아가거나 쓰기가 사라질 수 있다. 영구 원장은 DB 의 커밋된 메시지이고, 수신 측은 재전송을 중복 처리하지 않아야 한다.
- 발신자는 XADD 결과를 모르면 같은 발화 ID 로 재시도하고, 처리 서비스가 DB 에서 중복을 막는다.
