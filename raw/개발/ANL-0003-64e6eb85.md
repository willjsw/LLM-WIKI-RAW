# 웹소켓 재접속 공백 구간 메시지 유실 대안 분석

## Analysis

문제: 대화별 소켓 위치(대화 ID → 인스턴스)를 Redis 에 두고 해당 인스턴스로 보내는 구조에서, 클라이언트가 다른 인스턴스로 재접속하면 '위치 갱신'과 '이력 조회' 사이에 도착한 메시지가 옛 인스턴스로 가서 빠질 수 있다.

대안 비교
- 파티션 단위 구독: 소켓이 그 파티션을 맡지 않은 인스턴스에 붙으면 이벤트를 못 받는다. 리스 소유자가 소켓 보유 인스턴스로 포워딩해야 한다.
- 인스턴스 간 재발행: 위치를 보고 다시 보내도 공백 구간은 그대로 남는다.
- 모든 인스턴스로 발송: 공백 대부분을 메우지만 끊긴 찰나는 여전히 빠진다. 인스턴스를 늘려도 처리량이 줄지 않고 폴링 부하가 생긴다. 최후 수단이다.
- 버리기 전 다른 연결 확인: 폴링 부하가 있고 엣지 케이스 테스트가 많이 필요하다.
- lastMessageId 비교: ID 가 순번이 아니라 시간순이면 마지막 ID 끼리 비교해서는 빈 곳을 알 수 없다. 각 메시지에 직전 메시지 ID(prevMessageId)를 실어 클라이언트가 체인 끊김을 감지하고 재조회해야 한다.
- 이력 조회 재시도(예: 3회): 구현이 간단한 절충안이지만 확률을 낮출 뿐이다.
- 규약 순서 고정: '위치 등록 → (구독 RECEIPT 확인) → 이력 조회' 순서를 클라이언트 규약에 넣는다.

추가 고려
- 이력 API 로 메울 수 없는 비영속 이벤트(입장 인사, 수락, 종료 알림 등)는 별도 보장이 필요하다.
- 위치 키에는 TTL 을 두고 요청이나 연결 유지 중 주기적으로 연장한다. 끊긴 연결의 위치가 오래 남지 않게 한다.
- 이후 설계는 리스 소유자가 위치를 조회해 소켓 보유 인스턴스로 전달하고, 소켓 보유 인스턴스가 클라이언트 처리 확답을 받은 뒤에만 원본 스트림을 XACK 하는 방향으로 정리됐다. 전달 경로가 끊겨도 PEL 에 남아 재시도된다.
